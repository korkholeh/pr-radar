# Decisions & assumptions (autonomous run)

Appended by agents whenever they choose between options without a human.
One `## ` section per step, oldest first — the orchestrator writes those headings,
so `grep -n '^## '` is the index and a session can read only the part it needs.


## architect


- [architect/design] Ten Django apps under `apps/` exactly as spec §3 names them, plus `config/`; no extra `api` or `reports` app — why: the chart JSON endpoints are three views inside `dashboards` and the export layer is a package next to the tables it mirrors, so a separate app would only add an import boundary — alternatives: separate `api` app, separate `reports` app, a single monolithic app.
- [architect/design] `scope_for_user(user) -> ScopeFilter` is the only authorization path, and every `selectors.py` function takes a `ScopeFilter` instead of starting from `Model.objects.all()` — why: the same data leaves through pages, htmx fragments, chart JSON, tables, CSV and XLSX, and per-view decorators protect the view but not the export — alternatives: per-view `PermissionRequiredMixin`, django-guardian, DB row-level security (impossible on SQLite).
- [architect/design] An out-of-scope project/repository id in a query string is dropped silently rather than answered with 403 — why: a 403 confirms the id exists to a user who should not know it — alternatives: 403, 404.
- [architect/design] `DailyRollup` stores only `counter` values (and ratio numerators/denominators); medians, percentiles and size buckets are computed from raw rows on read; `state` metrics are reconstructed from dates — why: a median of daily medians is not the period median, and spec §8.3 forbids it — alternatives: roll up everything, roll up nothing, per-day t-digest sketches (deferred to ~10× data).
- [architect/design] Rollups are rebuilt from a dirty-days set recorded during post-processing, by deleting and rewriting exactly the affected `(date, scope, scope_id, cohort, metric_key)` rows — why: makes a half-finished rollup self-healing on the next run and makes `recompute --from --to` the single repair tool — alternatives: incremental counter updates, full nightly rebuild.
- [architect/design] Metric cache key includes a `last_data_version` integer incremented at the end of every sync and recompute, rather than deleting cache keys on write — why: one integer to get right instead of a matrix of key patterns to enumerate — alternatives: explicit key invalidation, short TTL, no cache.
- [architect/assumption] `httpx` timeouts are connect 10 s / read 30 s, and retries are 5 attempts with exponential backoff and jitter capped at 60 s — why: spec §5.4 requires retries on 502/503/secondary limits but gives no numbers — alternatives: shorter caps, unlimited retries.
- [architect/assumption] `Repository.sync_cursor` is kept as a field but correctness in v1 rests on the time watermark plus `SYNC_OVERLAP`; `last_synced_at` advances only after a whole repository finishes — why: a per-page watermark trades a cheap re-read for a permanent gap when a page fails after the watermark moved — alternatives: per-page resume, cursor-only resume.
- [architect/design] A nested GraphQL connection (reviews, comments, commits, files) that cannot be fully paginated fails that PR loudly instead of storing a truncated list — why: silently short data corrupts a metric, which is worse than a visible gap in `SyncRun.error_log` — alternatives: store what arrived, retry forever.
- [architect/design] Every huey task is a three-line wrapper over a service function that a management command calls directly, and the worker runs a single thread — why: the operator is one person on a laptop who will find the worker stopped, and SQLite has one writer so a second thread mostly produces `database is locked` — alternatives: Celery+Redis, threads in the web process, cron-only with no worker.
- [architect/assumption] On worker startup, `ExportJob` rows stuck in `running` for more than one hour are marked `failed` — why: otherwise the htmx progress poll never terminates after a killed worker — alternatives: no sweep, a heartbeat column.
- [architect/design] Huey uses its own `DATA_DIR/huey.sqlite3`, separate from `db.sqlite3` — why: frequent short queue writes and rare long domain writes should not share one write lock — alternatives: one database file, a non-SQLite broker.
- [architect/design] Tests run with `HUEY = {"immediate": True}`; the two paths that must not be inline (large-export hand-off, "button enqueues rather than blocks") assert the enqueue instead of the execution — why: keeps task code covered without a queue process in the test run — alternatives: a real consumer in tests, mocking the task decorator.
- [architect/decision] Tailwind version is pinned by the run and mapped onto the token variables explicitly: v4 via `@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *))` + `@theme inline`, or v3 via `darkMode: ['selector', '[data-theme="dark"]']` — why: spec §10.5's snippet is v3 syntax while the current line is v4 (latest release checked: v4.3.3), and only the attribute-bound dark variant satisfies the three-state stored preference — alternatives: Tailwind's default `prefers-color-scheme` dark mode, `class="dark"`, hand-written CSS, Pico.css (rejected at intake).
- [architect/decision] The Tailwind standalone binary is downloaded on demand into a git-ignored `.tools/` by `make css`, not committed — why: a ~100 MB platform-specific artefact does not belong in the repository, while the ~50 KB generated `static/css/app.css` does — alternatives: commit the binary, npm + PostCSS (rejected at intake), a CDN build.
- [architect/design] A test asserts `static/css/app.css` contains every token name defined in `tokens.css` — why: the stylesheet is a generated file under version control and can silently go stale after a template change — alternatives: rebuild CSS in the test gate (needs the binary and a network fetch in CI), no check.
- [architect/decision] `config/settings/e2e.py` is added alongside spec §13's `base`/`local`/`prod`, as prod plus a localhost `ALLOWED_HOSTS` and a separate e2e database — why: the e2e suite must run with `DEBUG=False` so a real 500 is a real error page, and it must not share the developer's database — alternatives: run e2e against `local` (hides 500s behind the debug page), env-var overrides on `prod`.
- [architect/decision] `make e2e-up` / `make e2e-down` are the e2e surface commands, with the Makefile created in phase 0 — why: the orchestrator accepts `make`, and backgrounding a server plus a worker and then blocking until the port answers cannot be expressed as a plain `&&` chain — alternatives: a shell script (refused by the orchestrator), a compose file (no containers in v1), `runserver` in the foreground (never returns).
- [architect/decision] E2E runs on port 8100 and `pytest`'s `testpaths` excludes `e2e/` — why: 8000 is the developer's own `runserver`, and the unit gate must not collect specs that need a live server — alternatives: 8001, a random port, a marker-based exclusion.
- [architect/decision] The lint gate is `ruff check` + `ruff format --check` + a bare `mypy` (with `files` pinned in `pyproject.toml` to `apps/metrics` and every `services.py`/`selectors.py`) + `makemigrations --check --dry-run` + `manage.py check` — why: spec §12 scopes mypy to `services/` and `metrics/`, and a model change without a migration must fail the build rather than surface at runtime — alternatives: `mypy apps` (types the whole project, far more churn), mypy path list on the command line, no migration check.
- [architect/assumption] Non-functional numbers the spec leaves open: 150 repositories and ~60 000 PRs before the design is revisited, 1–5 named users with ≤3 concurrent sessions, a 50-repo incremental sync under 30 minutes, `busy_timeout=5000 ms`, warm-cache dashboard under 300 ms, list page under 800 ms, background export ≤5 min for 200 k rows, churn ≤4 concurrent git workers, `runserver` ready in under 5 s — why: spec §14 phase 10 gives only "50 repos / 20k PRs" and "< 1.5 s", and the rest are needed to size indexes, timeouts and the rollup strategy — alternatives: leaving them unstated and discovering them in phase 10.
- [architect/assumption] Backup and restore is "stop both processes, copy `DATA_DIR`", documented in `docs/SETUP.md`, with `dumpdata` of the operator-owned models as the portable form — why: the spec names no backup story, and the operator-owned data (projects, identity mapping, policy, violation decisions, notes) cannot be recovered by re-syncing GitHub — alternatives: an automated snapshot task, no documented story.
- [architect/assumption] A failed `git fetch` or corrupt bare clone is deleted and re-cloned once, then reported as `ChurnResult.status='error'` — why: clones are disposable derived data and a half-fetched clone would poison every later blame — alternatives: fail immediately, retry indefinitely.
- [architect/design] `PolicyViolation` and `GitHubConnection.last_check_result` store a code plus parameters and never a rendered message; the same holds for sync errors shown in the UI — why: storing English text would freeze the wording at write time and make the Ukrainian UI permanently half-translated — alternatives: store rendered text, store both.
- [architect/design] `ReviewComment` stores only length and metadata, never comment text; `PullRequest.body` is stored because disclosure parsing needs it — why: less data about named people, less to leak, less to explain — alternatives: store all bodies behind `STORE_RAW_PAYLOADS`.
- [architect/design] Auto-resolve moves violations only `open → resolved` with an automatic marker, and never touches `acknowledged` or `waived` — why: those two states are a lead's recorded judgement about a person and must not be overwritten by a re-run — alternatives: auto-resolve any state, no auto-resolve.
- [architect/design] `conftest.py` installs a `respx` default that fails on any unmocked outbound request — why: the intake forbids a live GitHub call at any point, and a test asserting fixtures is not the same as a guarantee that nothing escaped — alternatives: trust the mocks, block the network at the OS level.

Latest Django 5.2 patch on PyPI: `5.2.17`. Latest Tailwind release: `v4.3.3` with `tailwindcss-macos-arm64` published.

## roadmap

- [roadmap/decision] The roadmap keeps spec §14's own eleven phases (0–10), numbering and order unchanged, rather than compressing them into the 3–10 range the step suggests — why: intake settled scope as "all phases 0 through 10 of section 14, in order", the order is already dependency-correct, and merging phases would make a phase exceed one focused session — alternatives: merge 0+1 (skeleton+models), merge 7+8 (all UI), re-derive an independent phase order.
- [roadmap/decision] `test_command` is confirmed as `uv run pytest -q`, unchanged from `.autodev/PROFILE.md` — why: it is the whole unit/integration suite from the repository root, non-interactive, and `testpaths = ["apps", "tests"]` keeps `e2e/` (which needs a live server) out of it — alternatives: `uv run pytest`, adding `-x`, including `e2e/` in the default run.
- [roadmap/verification] The command cannot be executed yet because no project skeleton exists: `ls /Users/korkholeh/Projects/pr-radar` → `.autodev  .git  docs` only, no `manage.py`, no `pyproject.toml`. `uv --version` → `uv 0.11.21 (5aa65dd7a 2026-06-11 aarch64-apple-darwin)`, so the runner itself is present. Phase 0 (`skeleton`) is the phase that must make `uv run pytest -q` work on a clean checkout.
- [roadmap/decision] Phases 0, 2, 3, 4, 5, 7, 8, 9 and 10 are marked `user_facing`; phases 1 (`data-model`) and 6 (`metrics-registry`) are not — why: 1 delivers only migrations plus Django admin and 6 delivers a registry plus a management command, neither of which adds a page or a flow a lead operates, while every other phase ships something visible in the app — alternatives: marking phase 1 user-facing because Django admin is a UI, marking every phase user-facing.
- [roadmap/assumption] Phase 3 owns both identity resolution and the derived PR fields, as spec §14 phase 3 groups them — why: the derived fields depend on identity (rubber stamp, self-merge and review rounds all need "not the author, not a bot"), so splitting them would force phase 4 to redo the wiring — alternatives: identity alone in 3 with derived fields moved into 4.
- [roadmap/assumption] `manage.py seed_e2e` is a separate command from `seed_demo`, created in phase 0 — why: `make e2e-up` in `.autodev/PROFILE.md` calls it in phase 0, while `seed_demo` (spec §5.5) is a phase 7 deliverable sized for UI development and profiling — alternatives: one command with a `--scale` flag from phase 0, e2e writing to the database directly.
- [roadmap/assumption] The `seed_demo --scale` option used for the phase 10 performance target (50 repositories / 20 000 PRs) is added in phase 10, not phase 7 — why: phase 7 needs readable demo data, phase 10 needs volume, and generating 20 k PRs on every phase-7 test run would be pure cost — alternatives: one fixed large seed from phase 7, a separate profiling fixture.
- [roadmap/assumption] Spec §10.6's two export types are split across phases: table export (CSV + XLSX, `columns.py`/`csv.py`/`xlsx.py`) lands in phase 7 with the tables it exports, and the multi-sheet dashboard report plus `ExportJob` background exports land in phase 8 — why: spec §14 already assigns the export layer to 7 and the reports to 8, and a report sheet cannot be written before the pages it summarises exist — alternatives: the whole export layer in 8, the whole export layer in 7.
- [roadmap/assumption] `ci_first_pass_rate` and `followup_fix_rate` are computed in phase 9 alongside churn, but are registered as `MetricDef`s in phase 6 returning `None` until then — why: spec §14 puts both in phase 9 while spec §8.2 lists them in the registry, and a registry with holes would break the `metrics_doc` freshness test and the dashboard KPI row — alternatives: registering them only in phase 9 (registry churn, doc regenerated twice), computing them early in 6 (needs `CheckStatus` semantics and the file-overlap heuristic before their phase).
- [roadmap/assumption] The four leak/isolation guarantees are asserted in the phase that introduces the exit, not once at the end: token leak in 2 (database, log, `error_log`, page) and again in 9 (git argv, remote URL, `.git/config`); project isolation in 8 across pages, chart JSON, CSV and XLSX separately — why: risks #2 and #3 are the two unrecoverable ones, and a single end-of-run audit would find them after ten phases of code assumed them safe — alternatives: one security phase at the end, a single combined leak test.
- [roadmap/assumption] `docs/METRICS.md` is generated in phase 6 and regenerated whenever the registry changes; the remaining `docs/*` user documentation is completed in phase 10, with `SETUP.md`, `CONFIGURATION.md` and `TRANSLATIONS.md` created in phase 0 and `GITHUB_CONNECTIONS.md` in phase 2 — why: a document is written by the phase that makes its content true, and the three phase-0 documents are what an operator needs to run the skeleton at all — alternatives: all documentation in phase 10, a documentation stub per phase.

## p01-plan


- [p01-plan/decision] `mypy.files` is `["apps/*/services.py", "apps/*/selectors.py"]` in phase 1 instead of `.autodev/PROFILE.md`'s longer list — why: mypy errors on a glob that matches nothing and `apps/metrics` does not exist until phase 7, which will append it — alternatives: `files = ["apps", "config"]` (types the whole project, rejected by the architect), passing paths on the command line, an empty stub `apps/metrics` package.
- [p01-plan/decision] `apps/dashboards` is created in phase 1 with a single placeholder Overview view at `/` — why: `base.html`, the navigation, the post-login redirect target and the e2e login spec all need one real page, and any other home would be moved again in phase 8 — alternatives: a `TemplateView` in `config/urls.py`, a home view inside `accounts`, no home page at all.
- [p01-plan/decision] The navigation renders only the items whose pages already exist, growing phase by phase, rather than spec §10.1's full list with dead links — why: a dead nav link answers 404 instead of the login redirect and breaks the parametrized `urlpatterns` test, and it misleads the operator — alternatives: disabled placeholder items, all items pointing at the Overview page.
- [p01-plan/decision] `make vendor` vendors htmx 2.0.10 only; `static/vendor/chart.umd.js` arrives in phase 8 — why: committing a ~200 KB artefact that no page loads and no test can keep honest is pure cost until the first chart exists — alternatives: vendoring both now, a CDN (rejected by the spec).
- [p01-plan/decision] Python/JS duration-formatter parity is proved by a shared case table (`tests/fixtures/duration_cases.json`) asserted in pytest for Python and in a Playwright spec for JS, rather than by running the JS in Node — why: `.autodev/PROFILE.md` states the project has no Node build, and the e2e browser is a JS runtime already in the test path — alternatives: a Node-based unit test, duplicating the expectations in two places, no parity test.
- [p01-plan/decision] SQLite pragmas (`journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`) are applied one statement at a time in a `connection_created` receiver in `config/db.py`, with `OPTIONS["transaction_mode"]="IMMEDIATE"` merged only for a SQLite `DATABASE_URL` — why: sqlite3 rejects a multi-statement `init_command`, and every SQLite-specific setting must vanish when `DATABASE_URL` points at PostgreSQL (ADR 0001) — alternatives: a multi-pragma `init_command`, a custom database backend, pragmas in `manage.py`.
- [p01-plan/decision] The colour-literal grep test excludes `static/css/tokens.css` (the token file), `static/css/app.css` (generated by Tailwind, which emits its own palette) and `static/vendor/`; staleness of the generated file is covered instead by the test that every `--token` name in `tokens.css` appears in `app.css` — why: scanning a generated stylesheet for hex would fail on Tailwind's own output and force the rule to be weakened — alternatives: grep `app.css` too (impossible), no exclusion list, no token-presence test.
- [p01-plan/decision] The `admin` and `lead` groups are created empty by an `accounts` data migration in phase 1; permissions are attached in phase 2 when `catalog.manage_settings` exists, and `UserProjectAccess` is deferred to phase 2 because it needs `catalog.Project` — why: keeps phase 1 free of the catalog dependency while `scope_for_user()` and the `ScopeFilter` contract still ship now — alternatives: creating a stub `Project` model early, deferring the groups to phase 2.
- [p01-plan/decision] `accounts.views.set_language` and `set_theme` are `@login_not_required` POST endpoints that write the cookie always and `UserPreference` only when authenticated — why: spec §10.5/§10.7 put both switchers on the login page, where no user exists yet — alternatives: switchers only after login, Django's built-in `set_language` plus a second authenticated view, a GET endpoint (rejected: it mutates).
- [p01-plan/verification] Environment facts this plan relies on, checked on 2026-09-17: `which msgfmt xgettext msgmerge` → `/opt/homebrew/bin/msgfmt`, `/opt/homebrew/bin/xgettext`, `/opt/homebrew/bin/msgmerge` (so `make messages` and `compilemessages` work); `uv --version` → `uv 0.11.21`; `ls ~/Library/Caches/ms-playwright` → `chromium-1234` present; `curl -sSI -L .../releases/download/v4.3.3/tailwindcss-macos-arm64` → `200` (Tailwind standalone v4.3.3 downloadable by `make css`); npm registry reports `tailwindcss` latest `4.3.3` and `htmx.org` latest `2.0.10` — both pinned at those versions.

## p01-implement

- [p01-implement] `UserLanguageMiddleware` overwrites `request.COOKIES[LANGUAGE_COOKIE_NAME]` instead of a session key — why: this Django pin (5.2.17) removed session-based i18n storage entirely; `django.utils.translation.LANGUAGE_SESSION_KEY` no longer exists and `LocaleMiddleware`/`get_language_from_request` resolve language from the cookie, Accept-Language and `LANGUAGE_CODE` only — alternatives: session key (does not exist on this Django version), a custom `process_request` reimplementation of `LocaleMiddleware`.
- [p01-implement] `e2e/support/auth.py::log_in` resets language to English after every login (via the real switcher, not a DB write) but leaves theme untouched — why: `e2e/web` personas are shared database rows reused across specs, so a language change made by one spec would leak into the next; theme is the one property `test_theme.py` itself owns end-to-end (including restoring it to `system` in a `finally` block), so a second reset point would fight the thing being tested — alternatives: reset both preferences on every login (breaks the fresh-login persistence assertion in `test_theme.py`), a fresh persona per spec (needs a second seed command), resetting via direct ORM writes (bypasses the product's own mechanism, against `e2e-authoring.md`).
- [p01-implement] `test_duration_format.py` loads `static/js/formatting.js` into the page with `page.add_script_tag(content=...)` reading the committed file directly, instead of via a `<script src>` tag — why: the file is not wired into any template yet (no chart consumes it until phase 8) and `STATICFILES_STORAGE` is `ManifestStaticFilesStorage`, so an unhashed `/static/js/formatting.js` URL 404s in the e2e environment — alternatives: add a script tag to `base.html` now (premature, no consumer), reference the hashed manifest name from Python (couples the test to Tailwind's hash), copy the file's source into the test (a second copy to keep in sync).

- [p01-review_fix1] Compile `locale/uk/LC_MESSAGES/*.mo` from a session-scoped autouse fixture in root `conftest.py` using `polib.pofile(...).save_as_mofile(...)` rather than shelling out to `msgfmt` or `manage.py compilemessages` — why: `.mo` is gitignored so a clean checkout has none and the translation tests failed (BLOCKER in REVIEW-r1), and `polib` is already a dev dependency, so this needs no assumption that `msgfmt` is installed on the machine running the tests — alternatives: commit `.mo` files, call `compilemessages` from conftest (recompiles Django's own bundled catalogues too, per the Makefile finding below).
- [p01-review_fix1] Huey immediacy for tests is set by mutating the real `huey.contrib.djhuey.HUEY` singleton's `.immediate` attribute directly in the `conftest.py` fixture (restored after each test), not by assigning `settings.HUEY` — why: REVIEW-r1 verified `djhuey` builds its `HUEY` instance once from the setting at app-ready time, so mutating `settings.HUEY` afterward (the phase-1 approach) never reached the running queue and the old test asserted the fixture's own assignment, not the queue — alternatives: a dedicated `config/settings/test.py`, monkeypatching `HUEY.immediate` per-test instead of via a shared autouse fixture.
- [p01-review_fix1] `apps/accounts/tests/test_settings.py`'s pragma test now calls `config.db.apply_sqlite_pragmas` directly against a real sqlite3 connection (and a fake-postgres connection for the no-op branch), plus a `django.db.connection` pragma check and a `configure_sqlite_transaction_mode` postgres no-op test — why: the old test executed `SQLITE_PRAGMAS` itself via a bare `sqlite3.connect()`, so it passed regardless of whether the `connection_created` receiver was even registered (MAJOR, risk #14 unmitigated) — alternatives: only testing through `django.db.connection` (can't observe `journal_mode=wal` reliably against the test DB, which pytest-django may run in-memory).
- [p01-review_fix1] Replaced `STATICFILES_STORAGE` (a no-op setting on this Django 5.2 pin) with a `STORAGES` dict in `config/settings/prod.py` (manifest storage for staticfiles) and dropped it from `base.py` entirely, so local/test fall back to Django's own default plain `StaticFilesStorage` — why: REVIEW-r1 verified at runtime that `STATICFILES_STORAGE` had zero effect and `settings.STORAGES` never changed — alternatives: keep the dead setting and only fix docs (rejected — the setting doing nothing is the actual bug).
- [p01-review_fix1] Turning manifest storage on for real surfaced a second, previously-masked bug: `collectstatic` crashes post-processing `static/css/src/input.css` because whitenoise's manifest post-processor tries to resolve `@import "tailwindcss";` as a relative file reference. Fixed by adding `--ignore=src` to the `collectstatic` call in `make e2e-up` and documenting the same flag for a future real deployment in `docs/SETUP.md` — why: `static/css/src/` is Tailwind CLI input, never meant to be served, and plain `StaticFilesStorage` never inspected file contents so this never fired before manifest storage was actually active — alternatives: move `static/css/src/` outside `STATICFILES_DIRS` (bigger restructuring of an established layout other tests/docs already reference), a custom `IGNORE_PATTERNS` finder setting.
- [p01-review_fix1] `config/settings/prod.py` now requires `SECRET_KEY` from the environment (`environ.Env().str("SECRET_KEY")`, no default) and raises `ImproperlyConfigured` if unset; `config/settings/e2e.py` sets `os.environ.setdefault("SECRET_KEY", "e2e-not-a-production-secret")` before importing `prod` — why: REVIEW-r1 (MINOR) found prod silently accepted the published dev default; e2e is a disposable localhost surface with no real secret to protect, so requiring an operator-supplied value there would only add friction — alternatives: a `.env` requirement enforced by the Makefile, a random key generated at `e2e-up` time.
- [p01-review_fix1] The CSS freshness guard is now a real checksum (`scripts/css_manifest.py`, sidecar `static/css/.build-manifest.sha256` written by `make css`, compared in `tests/test_css_tokens.py::test_app_css_is_not_stale`) over `tokens.css` + `src/input.css` + every `.html`/`.py`/`.js` under `templates/`, `apps/`, `static/js/` — why: REVIEW-r1 (MAJOR) proved the old test passed by construction since `@import "../tokens.css"` inlines every token into `app.css` regardless of staleness — alternatives: parse templates for utility classes and check each resolves in `app.css` (the review's other suggested fix; more precise but more code to keep correct). Trade-off accepted: this makes `make css` necessary after *any* Python change under `apps/`, not just template edits, which is conservative rather than precise — later phases should expect to run `make css` as part of their own green-gate pass whenever they touch `apps/`.

## p03-plan


- [p03-plan/decision] The "one sync at a time" lock is a new `github_sync.SyncLock` model (unique `name`, `acquired_at`, `sync_run` FK) acquired by `objects.create(name="global")` — an `IntegrityError` means another run holds it — released in a `finally`, and stolen when `acquired_at` is older than the new `SYNC_LOCK_STALE_MINUTES` (360) setting — why: ADR 0003 says "a lock row in the database" without naming a mechanism, and `select_for_update()` is silently a no-op on SQLite (ADR 0001 keeps us ORM-only and portable), so a uniqueness constraint is the portable equivalent; a killed worker otherwise leaves the row and wedges the tool forever, which no operator could fix from the UI — alternatives: `select_for_update` on a fixed row (no-op on SQLite, so the second run would proceed), a file lock in `DATA_DIR` (invisible to the UI and useless once the tool moves to a server, §13), reusing `SyncRun(status=running)` as the lock (a crashed run leaves a permanently "running" row and the same staleness problem without a dedicated timestamp).
- [p03-plan/decision] Eight new `AppSetting` keys in the `sync` group seeded by `catalog/0003_sync_settings.py`: `SYNC_OVERLAP_MINUTES=60`, `SYNC_PR_PAGE_SIZE=50`, `SYNC_NESTED_PAGE_SIZE=100`, `RATE_LIMIT_MIN_REMAINING=200`, `SYNC_MAX_RETRIES=5`, `SYNC_RETRY_MAX_SECONDS=60`, `SYNC_LOCK_STALE_MINUTES=360`, `TOKEN_EXPIRY_WARNING_DAYS=14`, `CONNECTION_RECHECK_MIN_MINUTES=60` — why: spec §5.3/§5.4 and ARCHITECTURE.md name every one of these numbers as behaviour the operator observes (and §5.1 makes the 14-day banner and the once-per-hour re-check rules), but phase 2's `SETTING_DEFS` shipped none of them, so without rows they would become magic constants scattered across `client.py` and `services.py` — alternatives: module-level constants in `github_sync` (untunable without a release, and invisible to the settings UI phase 7 builds), Django settings in `base.py` (would need an `.env` edit and a restart for a number an operator legitimately tunes per organisation).
- [p03-plan/decision] `GITHUB_API_BASE_URL` (default `https://api.github.com`) and the derived `GITHUB_GRAPHQL_URL` are **Django settings** read from `.env`, not `AppSetting` rows — why: they are deployment wiring rather than operator policy, and they are what `respx` routes bind to, so a database row could change them under a running test and break the "no unmocked outbound request" guarantee; GHES support later is then one env var — alternatives: `AppSetting` rows (mutable at runtime under the test guard, and meaningless to tune per-day), hardcoding the hostname (no GHES path at all, and nothing for respx to pin explicitly).
- [p03-plan/decision] Connections, repositories and sync runs are read through `services.py`, not a `selectors.py` — why: this follows the p02 precedent set for `policy.services.current_policy()`; CLAUDE.md requires every function in a `selectors.py` to start from `scope_for_user(user)`, and these three are global, admin-scoped configuration rather than per-project data, so keeping them out of `selectors.py` leaves the authorization rule absolute instead of carving a documented exception into the one choke point — alternatives: a `selectors.py` with an exemption comment (erodes the rule the moment a second exception appears), routing them through `scope_for_user()` anyway (a `ScopeFilter` that means nothing for a table with no project FK).
- [p03-plan/decision] `github_sync.pipeline.process_pull_request(pull_request_id)` ships in this phase as a defined, imported, no-op function called via `transaction.on_commit`, with a test asserting it runs exactly once per synced PR — why: spec §5.3 step 4 and ADR 0003 make the hook part of the sync contract, and shipping the call site plus its once-per-PR test now means phases 4–6 add stages without reopening the orchestrator; an empty function with a passing test is a smaller lie than an orchestrator that later grows a call site nobody tested — alternatives: add the hook in phase 4 (the orchestrator and its transaction-boundary tests would be rewritten then), call the four stages directly from `sync_repository` (couples the sync loop to four apps that do not exist yet).
- [p03-plan/decision] The single decrypt accessor is `apps/connections/services.py::plaintext_token(connection)`, with the raw `MultiFernet` work in a model-free `apps/connections/crypto.py`, and a grep test asserting `decrypt_token(` appears nowhere in `apps/` outside those two modules and their tests; `PATAuth` overrides `__repr__`/`__str__` to print only `connection_id` — why: ADR 0004 requires one accessor and plaintext only in a local variable, but "one accessor" is a convention until something enforces it, and the realistic leak path is not a `print()` — it is a token sitting in a dataclass's default `repr` that a traceback or a test failure renders — alternatives: a property on the model (invites `connection.token` in a template or an f-string), rely on review discipline alone (risk #2 is the one whose damage is not undoable).
- [p03-plan/decision] `errors.require(payload, path)` raises `GitHubSchemaError` carrying only the dotted JSON path, and `errors.optional(payload, path)` returns `None` (never `0`); no error message ever embeds the payload — why: the acceptance criterion asks the error to name the JSON path, and a GitHub response body can legitimately contain a token-shaped string (e.g. in a PR body a developer pasted), so quoting the payload into an exception would route untrusted text straight into `SyncRun.error_log` and defeat the leak test — alternatives: include a truncated payload for debuggability (a token fragment fits in any truncation), a generic `KeyError` (the criterion explicitly requires the path).
- [p03-plan/decision] Repository discovery fetches through GraphQL (`repositoryOwner(login:).repositories` when `owner_login` is set, `viewer.repositories` otherwise) and does **not** persist the fetched list; only the repositories an admin ticks become rows — why: a fine-grained PAT is issued per resource owner so `owner_login` is the natural root, classic PATs have no single owner and need `viewer`, and persisting the full list would create `Repository` rows the operator never chose and that `PROTECT` then makes awkward to remove — alternatives: REST `/user/repos` (a second pagination style and a second shape to fixture for no gain), persist everything with an `is_active` flag (spec §5.2 treats adding a repository as a deliberate act, and the repositories list would fill with client repos nobody syncs).
- [p03-plan/decision] `GitHubClient` takes an injected `sleep` callable, and every rate-limit and backoff test asserts the *durations requested* rather than waiting — why: the phase must test a wait-until-`resetAt` pause and a five-attempt exponential backoff capped at 60 s; real sleeps would add minutes to `uv run pytest -q` and make the suite flaky on a loaded machine — alternatives: `freezegun` alone (it does not intercept `time.sleep`), `monkeypatch.setattr(time, "sleep")` per test (the same thing without a declared seam, and it would silently stop working if the client switched to `httpx`'s own retry timing).
