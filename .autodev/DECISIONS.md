# Decisions & assumptions (autonomous run)

Appended by agents whenever they choose between options without a human.
One `## ` section per step, oldest first — the orchestrator writes those headings,
so `grep -n '^## '` is the index and a session can read only the part it needs.


## architect


- [architect/design] Ten Django apps under `apps/` exactly as spec §3 names them, plus `config/`; no extra `api` or `reports` app — why: the chart JSON endpoints are three views inside `dashboards` and the export layer is a package next to the tables it mirrors, so a separate app would only add an import boundary — alternatives: separate `api` app, separate `reports` app, a single monolithic app.
- [architect/design] `scope_for_user(user) -> ScopeFilter` is the only authorization path, and every `selectors.py` function takes a `ScopeFilter` instead of starting from `Model.objects.all()` — why: the same data leaves through pages, htmx fragments, chart JSON, tables, CSV and XLSX, and per-view decorators protect the view but not the export — alternatives: per-view `PermissionRequiredMixin`, django-guardian, DB row-level security (impossible on SQLite).
- [architect/design] An out-of-scope project/repository id in a query string is dropped silently rather than answered with 403 — why: a 403 confirms the id exists to a user who should not know it — alternatives: 403, 404.
- [architect/design] `DailyRollup` stores only `counter` values (and ratio numerators/denominators); medians, percentiles and size buckets are computed from raw rows on read; `state` metrics are reconstructed from dates — why: a median of daily medians is not the period median, and spec §8.3 forbids it — alternatives: roll up everything, roll up nothing, per-day t-digest sketches (deferred to ~10× data).
- [architect/design] Rollups are rebuilt from a dirty-days set recorded during post-processing, by deleting and rewriting exactly the affected `(date, scope, scope_id, cohort, metric_key)` rows — why: makes a half-finished rollup self-healing on the next run and makes `recompute --from --to` the single repair tool — alternatives: incremental counter updates, full nightly rebuild.
- [architect/design] Metric cache key includes a `last_data_version` integer incremented at the end of every sync and recompute, rather than deleting cache keys on write — why: one integer to get right instead of a matrix of key patterns to enumerate — alternatives: explicit key invalidation, short TTL, no cache.
- [architect/assumption] `httpx` timeouts are connect 10 s / read 30 s, and retries are 5 attempts with exponential backoff and jitter capped at 60 s — why: spec §5.4 requires retries on 502/503/secondary limits but gives no numbers — alternatives: shorter caps, unlimited retries.
- [architect/assumption] `Repository.sync_cursor` is kept as a field but correctness in v1 rests on the time watermark plus `SYNC_OVERLAP`; `last_synced_at` advances only after a whole repository finishes — why: a per-page watermark trades a cheap re-read for a permanent gap when a page fails after the watermark moved — alternatives: per-page resume, cursor-only resume.
- [architect/design] A nested GraphQL connection (reviews, comments, commits, files) that cannot be fully paginated fails that PR loudly instead of storing a truncated list — why: silently short data corrupts a metric, which is worse than a visible gap in `SyncRun.error_log` — alternatives: store what arrived, retry forever.
- [architect/design] Every huey task is a three-line wrapper over a service function that a management command calls directly, and the worker runs a single thread — why: the operator is one person on a laptop who will find the worker stopped, and SQLite has one writer so a second thread mostly produces `database is locked` — alternatives: Celery+Redis, threads in the web process, cron-only with no worker.
- [architect/assumption] On worker startup, `ExportJob` rows stuck in `running` for more than one hour are marked `failed` — why: otherwise the htmx progress poll never terminates after a killed worker — alternatives: no sweep, a heartbeat column.
- [architect/design] Huey uses its own `DATA_DIR/huey.sqlite3`, separate from `db.sqlite3` — why: frequent short queue writes and rare long domain writes should not share one write lock — alternatives: one database file, a non-SQLite broker.
- [architect/design] Tests run with `HUEY = {"immediate": True}`; the two paths that must not be inline (large-export hand-off, "button enqueues rather than blocks") assert the enqueue instead of the execution — why: keeps task code covered without a queue process in the test run — alternatives: a real consumer in tests, mocking the task decorator.
- [architect/decision] Tailwind version is pinned by the run and mapped onto the token variables explicitly: v4 via `@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *))` + `@theme inline`, or v3 via `darkMode: ['selector', '[data-theme="dark"]']` — why: spec §10.5's snippet is v3 syntax while the current line is v4 (latest release checked: v4.3.3), and only the attribute-bound dark variant satisfies the three-state stored preference — alternatives: Tailwind's default `prefers-color-scheme` dark mode, `class="dark"`, hand-written CSS, Pico.css (rejected at intake).
- [architect/decision] The Tailwind standalone binary is downloaded on demand into a git-ignored `.tools/` by `make css`, not committed — why: a ~100 MB platform-specific artefact does not belong in the repository, while the ~50 KB generated `static/css/app.css` does — alternatives: commit the binary, npm + PostCSS (rejected at intake), a CDN build.
- [architect/design] A test asserts `static/css/app.css` contains every token name defined in `tokens.css` — why: the stylesheet is a generated file under version control and can silently go stale after a template change — alternatives: rebuild CSS in the test gate (needs the binary and a network fetch in CI), no check.
- [architect/decision] `config/settings/e2e.py` is added alongside spec §13's `base`/`local`/`prod`, as prod plus a localhost `ALLOWED_HOSTS` and a separate e2e database — why: the e2e suite must run with `DEBUG=False` so a real 500 is a real error page, and it must not share the developer's database — alternatives: run e2e against `local` (hides 500s behind the debug page), env-var overrides on `prod`.
- [architect/decision] `make e2e-up` / `make e2e-down` are the e2e surface commands, with the Makefile created in phase 0 — why: the orchestrator accepts `make`, and backgrounding a server plus a worker and then blocking until the port answers cannot be expressed as a plain `&&` chain — alternatives: a shell script (refused by the orchestrator), a compose file (no containers in v1), `runserver` in the foreground (never returns).
- [architect/decision] E2E runs on port 8100 and `pytest`'s `testpaths` excludes `e2e/` — why: 8000 is the developer's own `runserver`, and the unit gate must not collect specs that need a live server — alternatives: 8001, a random port, a marker-based exclusion.
- [architect/decision] The lint gate is `ruff check` + `ruff format --check` + a bare `mypy` (with `files` pinned in `pyproject.toml` to `apps/metrics` and every `services.py`/`selectors.py`) + `makemigrations --check --dry-run` + `manage.py check` — why: spec §12 scopes mypy to `services/` and `metrics/`, and a model change without a migration must fail the build rather than surface at runtime — alternatives: `mypy apps` (types the whole project, far more churn), mypy path list on the command line, no migration check.
- [architect/assumption] Non-functional numbers the spec leaves open: 150 repositories and ~60 000 PRs before the design is revisited, 1–5 named users with ≤3 concurrent sessions, a 50-repo incremental sync under 30 minutes, `busy_timeout=5000 ms`, warm-cache dashboard under 300 ms, list page under 800 ms, background export ≤5 min for 200 k rows, churn ≤4 concurrent git workers, `runserver` ready in under 5 s — why: spec §14 phase 10 gives only "50 repos / 20k PRs" and "< 1.5 s", and the rest are needed to size indexes, timeouts and the rollup strategy — alternatives: leaving them unstated and discovering them in phase 10.
- [architect/assumption] Backup and restore is "stop both processes, copy `DATA_DIR`", documented in `docs/SETUP.md`, with `dumpdata` of the operator-owned models as the portable form — why: the spec names no backup story, and the operator-owned data (projects, identity mapping, policy, violation decisions, notes) cannot be recovered by re-syncing GitHub — alternatives: an automated snapshot task, no documented story.
- [architect/assumption] A failed `git fetch` or corrupt bare clone is deleted and re-cloned once, then reported as `ChurnResult.status='error'` — why: clones are disposable derived data and a half-fetched clone would poison every later blame — alternatives: fail immediately, retry indefinitely.
- [architect/design] `PolicyViolation` and `GitHubConnection.last_check_result` store a code plus parameters and never a rendered message; the same holds for sync errors shown in the UI — why: storing English text would freeze the wording at write time and make the Ukrainian UI permanently half-translated — alternatives: store rendered text, store both.
- [architect/design] `ReviewComment` stores only length and metadata, never comment text; `PullRequest.body` is stored because disclosure parsing needs it — why: less data about named people, less to leak, less to explain — alternatives: store all bodies behind `STORE_RAW_PAYLOADS`.
- [architect/design] Auto-resolve moves violations only `open → resolved` with an automatic marker, and never touches `acknowledged` or `waived` — why: those two states are a lead's recorded judgement about a person and must not be overwritten by a re-run — alternatives: auto-resolve any state, no auto-resolve.
- [architect/design] `conftest.py` installs a `respx` default that fails on any unmocked outbound request — why: the intake forbids a live GitHub call at any point, and a test asserting fixtures is not the same as a guarantee that nothing escaped — alternatives: trust the mocks, block the network at the OS level.
- [architect/verification] Environment claims in `.autodev/PROFILE.md` were checked, not assumed: `uv --version` → `uv 0.11.21`; `python3 --version` → `Python 3.13.3`; `git --version` → `git version 2.50.1 (Apple Git-155)`; `python3 -c "import sqlite3; print(sqlite3.sqlite_version)"` → `3.49.1`; `curl -sSI https://pypi.org/simple/` → `HTTP/2 200` and `curl -sSI https://github.com` → `HTTP/2 200` (so the network **is** available to `uv sync`, `make css` and `make vendor` — the no-GitHub-API rule is an intake constraint, not an environment limitation); `ls ~/Library/Caches/ms-playwright/` → `chromium-1234`, `chromium_headless_shell-1234`, `ffmpeg-1011` (browsers already installed). Latest Django 5.2 patch on PyPI: `5.2.17`. Latest Tailwind release: `v4.3.3` with `tailwindcss-macos-arm64` published.

## roadmap

- [roadmap/decision] The roadmap keeps spec §14's own eleven phases (0–10), numbering and order unchanged, rather than compressing them into the 3–10 range the step suggests — why: intake settled scope as "all phases 0 through 10 of section 14, in order", the order is already dependency-correct, and merging phases would make a phase exceed one focused session — alternatives: merge 0+1 (skeleton+models), merge 7+8 (all UI), re-derive an independent phase order.
- [roadmap/decision] `test_command` is confirmed as `uv run pytest -q`, unchanged from `.autodev/PROFILE.md` — why: it is the whole unit/integration suite from the repository root, non-interactive, and `testpaths = ["apps", "tests"]` keeps `e2e/` (which needs a live server) out of it — alternatives: `uv run pytest`, adding `-x`, including `e2e/` in the default run.
- [roadmap/verification] The command cannot be executed yet because no project skeleton exists: `ls /Users/korkholeh/Projects/pr-radar` → `.autodev  .git  docs` only, no `manage.py`, no `pyproject.toml`. `uv --version` → `uv 0.11.21 (5aa65dd7a 2026-06-11 aarch64-apple-darwin)`, so the runner itself is present. Phase 0 (`skeleton`) is the phase that must make `uv run pytest -q` work on a clean checkout.
- [roadmap/decision] Phases 0, 2, 3, 4, 5, 7, 8, 9 and 10 are marked `user_facing`; phases 1 (`data-model`) and 6 (`metrics-registry`) are not — why: 1 delivers only migrations plus Django admin and 6 delivers a registry plus a management command, neither of which adds a page or a flow a lead operates, while every other phase ships something visible in the app — alternatives: marking phase 1 user-facing because Django admin is a UI, marking every phase user-facing.
- [roadmap/assumption] Phase 3 owns both identity resolution and the derived PR fields, as spec §14 phase 3 groups them — why: the derived fields depend on identity (rubber stamp, self-merge and review rounds all need "not the author, not a bot"), so splitting them would force phase 4 to redo the wiring — alternatives: identity alone in 3 with derived fields moved into 4.
- [roadmap/assumption] `manage.py seed_e2e` is a separate command from `seed_demo`, created in phase 0 — why: `make e2e-up` in `.autodev/PROFILE.md` calls it in phase 0, while `seed_demo` (spec §5.5) is a phase 7 deliverable sized for UI development and profiling — alternatives: one command with a `--scale` flag from phase 0, e2e writing to the database directly.
- [roadmap/assumption] The `seed_demo --scale` option used for the phase 10 performance target (50 repositories / 20 000 PRs) is added in phase 10, not phase 7 — why: phase 7 needs readable demo data, phase 10 needs volume, and generating 20 k PRs on every phase-7 test run would be pure cost — alternatives: one fixed large seed from phase 7, a separate profiling fixture.
- [roadmap/assumption] Spec §10.6's two export types are split across phases: table export (CSV + XLSX, `columns.py`/`csv.py`/`xlsx.py`) lands in phase 7 with the tables it exports, and the multi-sheet dashboard report plus `ExportJob` background exports land in phase 8 — why: spec §14 already assigns the export layer to 7 and the reports to 8, and a report sheet cannot be written before the pages it summarises exist — alternatives: the whole export layer in 8, the whole export layer in 7.
- [roadmap/assumption] `ci_first_pass_rate` and `followup_fix_rate` are computed in phase 9 alongside churn, but are registered as `MetricDef`s in phase 6 returning `None` until then — why: spec §14 puts both in phase 9 while spec §8.2 lists them in the registry, and a registry with holes would break the `metrics_doc` freshness test and the dashboard KPI row — alternatives: registering them only in phase 9 (registry churn, doc regenerated twice), computing them early in 6 (needs `CheckStatus` semantics and the file-overlap heuristic before their phase).
- [roadmap/assumption] The four leak/isolation guarantees are asserted in the phase that introduces the exit, not once at the end: token leak in 2 (database, log, `error_log`, page) and again in 9 (git argv, remote URL, `.git/config`); project isolation in 8 across pages, chart JSON, CSV and XLSX separately — why: risks #2 and #3 are the two unrecoverable ones, and a single end-of-run audit would find them after ten phases of code assumed them safe — alternatives: one security phase at the end, a single combined leak test.
- [roadmap/assumption] `docs/METRICS.md` is generated in phase 6 and regenerated whenever the registry changes; the remaining `docs/*` user documentation is completed in phase 10, with `SETUP.md`, `CONFIGURATION.md` and `TRANSLATIONS.md` created in phase 0 and `GITHUB_CONNECTIONS.md` in phase 2 — why: a document is written by the phase that makes its content true, and the three phase-0 documents are what an operator needs to run the skeleton at all — alternatives: all documentation in phase 10, a documentation stub per phase.
