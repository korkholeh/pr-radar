# Risk register — PR Radar

Ordered by expected cost (likelihood × impact). "Where it is handled" names the phase from spec §14 and the
component that owns the mitigation.

| # | Risk | Likelihood | Impact | Mitigation | Where it is handled |
|---|---|---|---|---|---|
| 1 | **The tool measures people, and a wrong number lands in a 1:1.** Bad identity mapping, a bot counted as a person, a median over three PRs, or a metric attributed to the wrong day makes a manager draw a false conclusion about a named individual. This is the product risk that outranks every technical one. | High | High | `MIN_SAMPLE`=5 greys any metric with too small a sample and labels it; unmapped identities are a visible queue and a counter, not a silent drop; bot logins and `exclude_from_metrics` people are removed from every metric and counted separately; `followup_fix_rate` is labelled a heuristic in the UI as the spec requires; the people table defaults to sorting by name, never a ranking; every metric has a hand-computed test including the Kyiv day boundary and a DST transition. | Phases 3, 6, 10 — `catalog` (identity), `metrics` (registry, `MIN_SAMPLE`), `dashboards` (labels, empty states) |
| 2 | **A GitHub token leaks** into the database in plaintext, a log line, `SyncRun.error_log`, an exception, a rendered page, an export file, or a `git` remote URL. It grants read access to client private source; the damage is not undoable by us. | Medium | High | Fernet/`MultiFernet` ciphertext in `token_encrypted` with keys only in `.env`; one decrypt accessor, plaintext only in a local variable; `SecretMaskingFilter` installed on the root logger in **phase 0**, before any token exists; `git` receives credentials only through `GIT_ASKPASS` + env, never in a URL, `.git/config` or `ps`; admin form omits the token field, UI shows `…last4` and offers no reveal; the spec §12 leak test searches DB, logs, `error_log`, HTML and export files after a *failing* sync and after an export. | Phases 0, 2, 9 — `connections`, `config` (logging), `churn` (ADR 0004) |
| 3 | **A restricted lead sees another project's data** through a path that is not a page — a chart JSON endpoint, a CSV download, or an XLSX report. Six exits, one rule, and the exports are where a check is forgotten. | Medium | High | `scope_for_user()` is the single choke point; selectors take a `ScopeFilter` rather than starting from `objects.all()`; out-of-scope ids in a query string are dropped silently rather than 403'd; a parametrized test walks `urlpatterns` asserting anonymous redirect for **every** URL; isolation is asserted separately on pages, chart JSON, CSV and XLSX. | Phases 0, 8 — `accounts` (ADR 0002), `dashboards/exports` |
| 4 | **The ten-hour ceiling stops the run mid-way through phases 7–10**, leaving the UI, exports, churn and the Ukrainian translation incomplete while phases 0–6 are done. The spec's phase order already front-loads the data layer, but the UI phases are the largest. | High | Medium | Phase order is the spec's own and is not reordered; each phase merges to `main` only after its full gate passes, so whatever completes is releasable; `docs/PROGRESS.md` is updated per phase with deviations and open questions; the roadmap step should keep phase 10 (polish) as the only phase whose omission costs nothing structural. | Roadmap step; every phase gate |
| 5 | **AI detection is wrong in both directions.** A false positive accuses someone of undisclosed AI use; a false negative makes the adoption number meaningless. The rules are regex heuristics over text that tool vendors change. | High | Medium | Rules live in editable `DetectionRule` rows seeded from `fixtures/detection_rules.yaml`, not in code, so a bad rule is fixed by the admin, not a release; every rule carries a `confidence`, and only `high` yields `ai_explicit`; disputed rules are seeded as `low`; `AISignal.evidence` stores the matching fragment so any claim is inspectable on the PR page; the settings UI has "test this rule against the last N PRs"; every detector has a positive *and* negative test. | Phase 4 — `ai_detection` |
| 6 | **Policy evaluation duplicates or resurrects violations**, so the compliance console fills with noise and a lead's `acknowledged`/`waived` judgement is overwritten by a re-run. | Medium | High | Uniqueness on `(pull_request, rule_code, details_hash)`; evaluation is idempotent by construction; auto-resolve moves only `open → resolved` and marks itself automatic — it never touches a human status; merge-dependent rules run only on merged PRs; `AIPolicy.effective_from` excludes older PRs; each of the nine rules has positive, negative, idempotency and auto-resolve tests. | Phase 5 — `policy` |
| 7 | **Metric correctness silently breaks** because a distribution metric gets rolled up, or a day boundary is computed in UTC instead of `Europe/Kyiv`. Plausible, wrong numbers are worse than an error. | Medium | High | `MetricDef.kind` decides storage: only `counter` (and ratio numerators/denominators) reach `DailyRollup`; medians and percentiles are computed from raw rows; one timezone helper owns every boundary; `recompute` rebuilds any range from raw data; `docs/METRICS.md` is generated from the registry and a test fails if it is stale. | Phase 6 — `metrics` (ADR 0007) |
| 8 | **Ukrainian translation lags behind the UI**, ending with a half-English interface — the classic failure of leaving i18n to the end. | High | Medium | The spec's per-phase rule: new UI strings get their Ukrainian translation *in the same phase*; system-generated text is stored as `rule_code` + params and rendered at read time, never as a baked English string; gates check `.po` freshness, no empty/fuzzy `msgstr`, and matching placeholders via `polib`; a smoke test renders every page in `en` and `uk` with a canary list of English strings that must not appear in the `uk` render. | Phases 0–10, every phase — `config` (i18n), all templates |
| 9 | **No GitHub credentials exist for this run (intake).** Everything about sync, connection verification, rate limiting and discovery is validated against fixtures only; a real-world schema or header mismatch would not be discovered tonight. | High | Medium | Accepted and bounded: fixtures under `tests/fixtures/github/` mirror real GraphQL response shapes; the client validates the shape it depends on and raises a named `GitHubSchemaError` with the JSON path rather than failing obscurely; `bootstrap_connection` and the verification flow are implemented and unit-tested; `docs/GITHUB_CONNECTIONS.md` documents a first-run checklist so the operator's first live sync is a deliberate, observable step. | Phase 2 — `github_sync`, `connections`; `docs/` |
| 10 | **Dashboards miss the 1.5 s budget** on 50 repos / 20 k PRs, because distribution metrics scan raw rows and templates hide N+1 queries. | Medium | Medium | Counters come from `DailyRollup`; results are cached under a key containing `last_data_version`; list views carry `assertNumQueries` tests so an N+1 fails the build; indexes and `select_related`/`prefetch_related` are a named task in phase 10, profiled against `seed_demo` at the stated volume; the fact-table escape hatch is documented in ADR 0007 and costs nothing today because `compute()` is the only reader. | Phases 6, 7, 10 — `metrics`, `dashboards` |
| 11 | **Churn is the most fragile feature**: it shells out to `git`, needs bare clones and disk, depends on `Contents: read`, and is meaningless for rebase merges. It is also last in the phase order, so it is the most likely to be reached while tired. | Medium | Medium | Failure is data, not an exception: `ChurnResult.status` carries `ok / unsupported_merge_method / too_large / error` with the reason; rebase merges are explicitly unsupported in v1; `CHURN_MAX_FILES`=50 and bounded parallelism; `lines_at_merge == 0` skips the result rather than recording 0 %; a failed fetch deletes and re-clones once, then reports `error`; tested against a temporary git repository built inside the test, covering squash and merge-commit cases. | Phase 9 — `churn` |
| 12 | **Both themes must be correct, and only one gets looked at.** Contrast failures, hard-coded colours and an unreadable dark heat map are easy to ship and tedious to find. | Medium | Medium | Colour exists only in `tokens.css`, and a grep test fails on any `#hex`/`rgb()` elsewhere; charts read colours at runtime and redraw on `themechange`; the page smoke test renders every page in **both** themes; contrast ratios are part of the token definition, not a later pass; status is never colour-only (arrows, icons, text badges). | Phases 0, 7, 10 — `dashboards`, `static/css` (ADR 0008) |
| 13 | **An export leaks or misbehaves**: a formula injection payload from a PR title executes in Excel, `Person.notes` reaches a report, or a 200 k-row export blocks a request. | Low | High | `strings_to_formulas=False` and an apostrophe prefix for CSV values starting with `= + - @`; `Person.notes` is excluded by construction and asserted absent by test; exports above `EXPORT_SYNC_MAX_ROWS` (20 000) become huey jobs with htmx polling; a generated file is downloadable only by its own author and is deleted after 7 days; every export writes an `AuditEntry`. | Phase 8 — `dashboards/exports` |
| 14 | **SQLite write contention**: sync, `recompute`, a background export and a dashboard write collide and produce `database is locked`. | Medium | Low | WAL + `busy_timeout=5000`; the queue lives in a separate database file; one sync at a time via a DB lock; one huey worker thread; churn bounds its own parallelism. The path out is `DATABASE_URL`, kept cheap by the ORM-only rule. | Phases 0, 2 — `config`, `github_sync` (ADR 0001) |
| 15 | **A generated artefact goes stale in the repository** — `static/css/app.css` after a template change, `docs/METRICS.md` after a registry change, or `.po` files after a new string. All are committed, so all can rot silently. | Medium | Low | A test asserts `app.css` contains every token name; `metrics_doc` has a freshness test; `.po` freshness and placeholder integrity are gate checks; `docs/SETUP.md` lists `make css` and `compilemessages` as explicit upgrade steps. | Phases 0, 6, 7 — build gates |
| 16 | **The `--merge-phases` setting writes unreviewed code to `main`** (accepted at intake, with the developer explicitly informed). A phase that passes its gate but is wrong lands on the default branch. | High | Low | Accepted by the developer. Bounded by the gate being real — `ruff check`, `ruff format --check`, `mypy`, `pytest` must all pass — by the prohibition on weakening any check to make it pass, by stacked draft PRs left open per phase for reading afterwards, and by `docs/PROGRESS.md` recording deviations per phase. | Orchestrator; every phase gate |
