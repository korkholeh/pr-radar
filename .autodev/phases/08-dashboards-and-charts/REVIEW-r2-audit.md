**Verdict:** changes_requested

The BLOCKER is genuinely fixed in the product: narrow_scope() is wired at all four Scope-building call sites (views.py:50, 94, 105, 181), ScopeFilter.repository_ids is propagated through activity._scoped, the catalog selectors and the compute() cache fingerprint, and I confirmed at runtime on a scratch test DB that a project-narrowed access changes a PERSON-scope compute_many result (2.0 -> 1.0). Lint gate and the affected test subset (dashboards, catalog, metrics, activity, tests) both exit 0, and the uk catalog survived the logged `git checkout -- locale/` incident intact (0 empty msgstr, phase-8 strings present). The cohort MINOR and the NIT are fixed with tests, and the XLSX delta colouring matches registry DIRECTIONS. Two majors remain. First, the MAJOR fix and the BLOCKER fix contradict each other: the unconditional '(org-wide)' column marker is false exactly when the new filter is applied, because narrowing makes the people-table metric values project/repository-scoped, so a filtered people export ships narrowed numbers under an org-wide label. ## [MAJOR] '(org-wide)' marker is false whenever the new project/repository filter is applied
`apps/dashboards/exports/columns.py`

_org_wide_title() (columns.py:79-90) suffixes every PEOPLE_COLUMNS metric title unconditionally, on the stated premise that 'the people table's metric values are always organization-wide'. The BLOCKER fix in the same diff falsifies that premise: with a project or repository selected, views pass a narrowed ScopeFilter into people_rows() -> compute_many(ScopeType.PERSON, access) -> compute() -> scoped_pull_requests() -> pull_requests_for_metrics(scope.access), so the values ARE narrowed. Verified on a scratch test DB: a person with one merged PR in project A and one in project B computes prs_merged=2.0 unrestricted and 1.0 under ScopeFilter(unrestricted=False, project_ids={A}). A lead who filters Overview to one project and exports People gets project-only numbers in a file whose every metric column is titled 'PRs merged (org-wide)', 'Lead time p50 (org-wide)' — the wrong number in a 1:1 that RISKS row 1 and the original MAJOR are about. rows.py:150-155's docstring ('the metric values themselves stay organization-wide') and the DECISIONS p08/review_fix2 bullet that argues the unconditional label are both false for the filtered case.

**Fix:** Make the marker request-scoped so it appears only where it is true — at scope_type != GLOBAL with no filter-bar narrowing. Either thread the Scope into the people TableSpec's column generation, or (cheaper) have views.export_table write the existing partials/table.html note as a CSV preamble line / XLSX first row under the same condition the HTML note uses. Then correct rows.py::people_rows' docstring and the DECISIONS bullet to say the values follow scope.access but not the page's project/repository scope.

## [MAJOR] No test covers the view wiring of narrow_scope — the blocker can regress silently
`apps/dashboards/views.py`

test_filter_narrowing.py exercises narrow_scope() as a unit and then calls build_dashboard(narrow_scope(scope, params), params) directly; the only view-level test (test_project_filter_round_trips_through_the_query_string, lines 175-184) asserts nothing but `value="<pk>" selected` in the body. The blocker was precisely that no consumer read the parsed ids, i.e. the four `scope = params_module.narrow_scope(scope, params)` lines at views.py:50, 94, 105 and 181. Deleting all four leaves the whole suite green — the same silent-green state that let the blocker ship in round 1. The review explicitly asked for 'a test asserting a project-filtered Overview KPI/table differs from the unfiltered one'; that assertion currently lives below the view boundary.

**Fix:** Add at least one page-level test: client.get(reverse('dashboards:overview'), {'preset': 'custom', 'from': ..., 'to': ..., 'project': str(project_a.pk)}) and assert the KPI value differs from the unfiltered request (1 vs 4 with the existing fixture shape). Ideally one more for dashboards:export (a project-filtered CSV has fewer rows) and one for chart_json, since those call sites are equally untested.

## [MINOR] _access_fingerprint renders None and an empty frozenset identically, so two different ScopeFilters share a cache key
`apps/metrics/services.py`

ScopeFilter's contract changed in this diff: with unrestricted=False, project_ids=None now means 'no restriction on this axis' (previously `project_ids or frozenset()` made it 'see nothing'). But _access_fingerprint (services.py:328-335) still collapses both through `access.project_ids or frozenset()`, so ScopeFilter(unrestricted=False, project_ids=None, repository_ids={7}) — what narrow_scope produces for a repository-only filter — and ScopeFilter(unrestricted=False, project_ids=frozenset(), repository_ids={7}) — what narrow_scope's intersection branch produces when a restricted lead picks a project they cannot see — both fingerprint as '|7' while meaning 'all projects' and 'no projects'. Not reachable today because scope_for_user() is still the unrestricted phase-1 stub, but it goes live the moment phase 9 turns per-user narrowing on, and it is exactly the cross-caller cache bleed RISKS row 3 guards.

**Fix:** Fingerprint each axis distinctly, e.g. '*' for None and an explicit empty marker for an empty frozenset, rather than letting both render as ''.
