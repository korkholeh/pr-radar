# Review — phase 10 round 2

**Verdict:** changes_requested

Round 2: all three r1 majors are genuinely fixed, each with a dedicated, non-vacuous test (deadline computed inside the worker, all four churn AppSettings read once on the main thread, deleted files contributing 0 instead of erroring), and the r1 minors/nits were handled too — timeouts threaded into every run_git call site, literal-credential masking on top of mask_secrets, the too_large limit stored per row, the follow-up cascade batched to O(1) queries, the slack query-count test dropped. All 21 PLAN tasks are checked with matching artifacts, no [~] anywhere, every deviation is logged in DECISIONS, and the full suite is green (exit 0). All seven acceptance criteria have proving tests, though the zero-lines criterion is now proved inverted by design. Three majors remain, all inside the r1 fix surface: _sum_blame's catch is too wide, so a blame timeout or a corrupt clone silently under-counts lines_at_merge (a wrong published ratio) or produces a terminal ok row that is never retried; _sum_surviving is the one unguarded git step in compute_churn_for_pull_request, so its failure escapes the PR and the new broad except Exception converts it into error/worker_failed for the entire repository, permanently stalling that repo if the failure is deterministic; and the PR export's Churn column is still hardcoded None in rows.py despite its own docstring deferring it to this phase, with no later phase owning it.

## [MAJOR] _sum_blame swallows every GitOperationError, not just a missing path — a transient git failure publishes a wrong ratio or settles the PR permanently
`apps/churn/services.py`

The r1 fix made `_sum_blame` (services.py:99-106) `continue` on *any* `GitOperationError`. Only the missing-path case is benign. A `reason="timeout"` failure (blame is now bounded by CHURN_GIT_TIMEOUT_SECONDS=120, so timeouts are a live outcome on a big file), or a corrupt/partially-fetched clone, silently drops that path's lines from `lines_at_merge`. Two consequences: (a) the PR gets an `ok` row with a ratio computed from an under-counted denominator — a wrong number attributed to a named person (RISKS row 1), with nothing in the row saying it is partial; (b) if every path fails, `lines_at_merge == 0` and the PR is now written as a *terminal* `status=ok` row (see the zero-lines change), so `eligible_pull_requests` never retries it and the PR never gets churn again. The whole point of the `error` status is that it is retried; this path converts retryable failures into permanent silent ones. `test_a_deleted_non_excluded_file_contributes_zero_rather_than_erroring` covers only the intended case; nothing covers a blame timeout.

**Fix:** Narrow the catch: `except GitOperationError as exc:` → re-raise (or record `blame_failed`) unless the path is genuinely absent — e.g. `if exc.reason == "timeout" or blame._path_exists_at(clone_dir, rev, path, timeout=timeout): raise`. Add a test monkeypatching `blame_counts` to raise `GitOperationError(..., reason="timeout")` and asserting `status == error` / `blame_failed`, not a silently smaller `lines_at_merge`.

## [MAJOR] _sum_surviving is unguarded, so one PR's blame failure marks the whole repository error/worker_failed
`apps/churn/services.py`

`compute_churn_for_pull_request` wraps `_pr_commit_set` and `_snapshot_sha` in try/except and its docstring states "Never raises", but the step-6 call `lines_surviving = _sum_surviving(...)` (services.py:192-194) is not wrapped. Both `resolve_path_at` (`git log --name-status -M` over merge_sha..snapshot_sha — expensive on a monorepo, now timeout-bounded) and `blame_counts` inside it can raise `GitOperationError`. It escapes the PR, escapes `_compute_repository`'s loop (no try there either), and lands in `run_churn`'s new broad `except Exception`, which discards the outcomes already computed for that repository and writes `error`/`worker_failed` for *every* PR of that repository. That directly contradicts PLAN §6 step 9 and the RISKS-row-11 promise that one PR's failure never aborts its repository. If the failure is deterministic (a pathological file that always times out on blame), the repository makes zero progress on every nightly run, forever, while still paying for the clone.

**Fix:** Wrap steps 5-6 in the same per-PR try/except used for `_snapshot_sha`, returning `_error_outcome(pr_id, window_days, "blame_failed", str(exc))`; additionally wrap the `compute_churn_for_pull_request(...)` call inside `_compute_repository`'s loop so no future bug can promote one PR's failure to a whole-repository failure. Test: monkeypatch `resolve_path_at` to raise for one PR and assert the other PRs of the same repository still get `ok` rows.

## [MAJOR] PR list/export Churn column is still hardcoded None after this phase computed the data
`apps/dashboards/rows.py`

`pull_request_rows()` returns `"churn_ratio": None` (rows.py:234) and its own docstring says `churn_ratio` is always None "until phase 10 computes ChurnResult". Phase 10 now computes it, but the row was never wired, so `PULL_REQUESTS_COLUMNS`' `ExportColumn("churn_ratio", _("Churn"), "percent")` (apps/dashboards/exports/columns.py:131) renders an always-blank column in the PR CSV/XLSX export. Spec §12 lists churn among the PR export's fields. ROADMAP phase 11 covers polish/perf/docs and does not claim this, and phase 10 is the last phase that owns churn — so nobody owns it after this merge, and the code comment pointing at phase 10 becomes permanently false.

**Fix:** Annotate the queryset with a `Subquery(ChurnResult.objects.filter(pull_request=OuterRef('pk'), window_days=get_int('CHURN_WINDOW_DAYS'), status=OK).values('churn_ratio')[:1])`, feed it into the row dict, update the docstring, and keep the PR-list `assertNumQueries` pin (one subquery, no N+1). If this is deliberately deferred, say so in DECISIONS and move the roadmap line, rather than leaving a blank user-visible export column.

## [MINOR] Zero lines_at_merge now writes a ChurnResult, inverting the phase's literal acceptance criterion
`apps/churn/services.py`

The criterion reads "A PR whose lines_at_merge is 0 records no ChurnResult rather than a 0% ratio" (spec §9.6: «результат пропускається»). The r1 fix changed this to a settled row `status=ok, lines_at_merge=0, churn_ratio=None`, and the proving test was renamed/rewritten to assert exactly that (`test_writes_one_row_per_computed_pr_and_a_ratio_less_row_for_zero_lines_at_merge`). The intent — never a fabricated 0% — is preserved, `percentile()` drops `None` from both value and sample size so `churn_21d` is unaffected, and the deviation is logged in DECISIONS under p10-review_fix1 with a real justification (otherwise the PR is re-cloned and re-blamed nightly forever). Flagging so the deviation is a conscious acceptance, not an unnoticed one: the cost is that `status=ok` now conflates "measured" with "nothing measurable", and that conflation is what makes the blame-swallow finding above permanent rather than retried.

**Fix:** Keep the settling behaviour, but distinguish it from a real measurement — e.g. only settle as `ok` when the blame calls all succeeded, and record `error`/`blame_failed` (retryable) when any of them failed. Either way, restate the criterion in PLAN.md's acceptance table so the contract and the test agree.
