# Audit of the round-2 fixes — phase 1

**Verdict:** changes_requested

All four REVIEW-r2 findings (1 major, 3 minors) are really fixed in the product, each with a test I confirmed fails without the fix; nothing was rejected. I re-ran every gate: `uv run pytest -q` 113 passed, the full lint chain clean, and a clean `git archive` export of the staged tree now renders Ukrainian (`gettext('Overview') -> 'Огляд'`) with no compile step, while deleting the committed `.mo` there makes 6 tests fail and editing a `.po` msgstr trips the new freshness test by name. Two problems the fixes themselves introduced: (1) the committed `static/css/app.css` is already stale against a fresh `make css` from the committed tree — Tailwind v4's automatic content detection ingests `.autodev/**` and root `tests/`, which the staleness manifest does not cover, so a fresh build emits `.bg-white` and `.text-gray-500` (strings present only in the fix session's own `.autodev/DECISIONS.md` entry) while `test_app_css_is_not_stale` stays green; this is risk #15's exact failure mode and it breaks the byte-identical-rebuild property both prior review rounds verified. (2) `.autodev/ARCHITECTURE.md:148` still declares `.mo` files "not committed", directly contradicting the shipped repository, with the same stale claim in `PROFILE.md` and `PLAN.md`. One minor: the committed `.mo` files were produced by the now-deleted polib fixture, not by `make messages`, so the first `make messages` run rewrites both binaries.

## [MAJOR] Committed app.css is already stale against a fresh `make css`, and the staleness gate cannot see it
`static/css/src/input.css`

Tailwind v4 scans the whole repository via automatic content detection in addition to the explicit `@source` directives, but `scripts/css_manifest.py` only hashes `templates/`, `apps/` and `static/js/`. Proof, run on the unmodified working tree: `./.tools/tailwindcss -i static/css/src/input.css -o /tmp/fresh-app.css --minify` produces a file that differs from the committed `static/css/app.css` at char 6546 — the fresh build additionally contains `.bg-white{background-color:var(--color-white)}` and `.text-gray-500{color:var(--color-gray-500)}`. `grep -rln 'bg-white|text-gray-500'` shows those strings exist only in `.autodev/DECISIONS.md`, i.e. in the fix session's own decision entry, written after it ran `make css`. Meanwhile `uv run pytest tests/test_css_tokens.py -q` passes, because the manifest hash does not cover `.autodev/**` or root `tests/`. Net effect of this diff: the generated artifact under version control no longer reproduces from its own tree, the guarantee both r1 and r2 verified by hand (`fresh Tailwind build byte-identical to the committed app.css`) is now false, and the drift is self-feeding — every future review/decision document that happens to mention a Tailwind palette class silently changes what `make css` emits while the freshness test reports green. This is exactly risk #15 (`a generated artefact goes stale in the repository`). The fix session logged the leak as 'harmless, left unfixed', but the logged rationale only covers the unused-utility bloat, not the broken reproducibility of the committed artifact or the blind spot in the gate.

**Fix:** Turn off automatic content detection so only the manifest-covered sources can affect the build: in `static/css/src/input.css` either add `@source not "../../../.autodev";` and `@source not "../../../tests";` next to the existing exclusions, or switch to explicit sourcing — `@import "tailwindcss" source(none);` plus the existing `@source` list. Then rerun `make css` and commit both `static/css/app.css` and `static/css/.build-manifest.sha256`; verify with `./.tools/tailwindcss -i static/css/src/input.css -o /tmp/fresh.css --minify && cmp /tmp/fresh.css static/css/app.css`.

## [MAJOR] ARCHITECTURE.md still states `.mo` files are not committed, contradicting what this diff ships
`.autodev/ARCHITECTURE.md`

The major fix committed `locale/uk/LC_MESSAGES/{django,djangojs}.mo` and dropped `*.mo` from `.gitignore`, but the architecture document — source of truth #2 for every later phase — was not updated. `.autodev/ARCHITECTURE.md:148` still reads `| .mo translation files | built by compilemessages, **not committed** | .po files are committed |`, and `:433` still gives the release procedure as `git pull && uv sync && migrate && compilemessages`. The same stale claim survives in `.autodev/PROFILE.md:41` ('.mo built, not committed'), `:131`, `.autodev/phases/01-skeleton/PLAN.md:216` (the `.gitignore` contents list includes `*.mo`) and `PLAN.md:332` (risk #15 mitigation row: '.mo files are not committed'). A `.autodev/DECISIONS.md` entry records the change, but the ordering the autodev rules impose puts ARCHITECTURE.md above code, so a later phase touching packaging or `.gitignore` will read a factual statement about the repository that is now false and can legitimately re-ignore `*.mo` — killing the Ukrainian UI on a clean install for a second time (the new test would catch it, but only after the regression is authored).

**Fix:** Update `.autodev/ARCHITECTURE.md:148` to state that `locale/uk/LC_MESSAGES/*.mo` are committed alongside `static/css/app.css` and are covered by `tests/test_translations.py::test_mo_catalog_matches_committed_po_source`, drop `compilemessages` from the upgrade command at `:433`, and correct the `.gitignore` contents list and the risk #15 mitigation row in `.autodev/phases/01-skeleton/PLAN.md` (and the two `PROFILE.md` lines if that file is in scope for phase steps).

## [MINOR] Committed .mo files were produced by the deleted polib fixture, not by `make messages`
`locale/uk/LC_MESSAGES/django.mo`

The committed binaries carry the mtime of the r1 `conftest.py` fixture run (08:27) and are polib output. Forcing the documented producer to rerun on an untouched clean copy (`touch locale/uk/LC_MESSAGES/*.po && manage.py compilemessages -l uk --ignore=.venv`) yields a byte-different file: md5 `8830841174876ba4ded2fa4704071c7f` vs the committed `b073ae78a989e1dd07aad90abe8e93d3`. Both are valid and semantically identical — the msgfmt-built copy passes `tests/test_translations.py` unchanged and the polib copy renders Ukrainian correctly — so this is noise, not breakage: the first developer who follows `docs/SETUP.md` and runs `make messages` gets a binary diff in both catalogues with no source change behind it, and the shipped artifact's producer is a code path that no longer exists in the repository.

**Fix:** Run `make messages` once and commit the resulting `.mo` files, so the committed artifact is the output of the command the docs tell everyone to use.
