## [MAJOR] `raw` payload column missing from five GitHub-owned models, contrary to spec §4 and the phase's own plan
`apps/activity/models.py`

Spec §4's preamble states: «Усі сутності з GitHub мають `github_id` (unique) і `raw` (JSONField, опційно, за прапорцем `STORE_RAW_PAYLOADS`)». PLAN.md's Design section repeats it as a field convention: "`raw = JSONField(null=True, blank=True)` on **every** GitHub-owned model. Writing it is gated by `settings.STORE_RAW_PAYLOADS` in the sync phase; the column is always present."

As shipped, `raw` exists on only three models — `catalog.Organization` (models.py:18), `catalog.Repository` (models.py:52), `activity.PullRequest` (models.py:98). It is absent from `activity.Commit`, `activity.Review`, `activity.ReviewComment` (all three are first-class GitHub nodes — each carries a unique `github_id`), and from `activity.PRFile` and `activity.CheckStatus` (GitHub-owned under the plan's wording, no node id of their own). `grep -n "raw = models.JSONField" apps/*/models.py` returns exactly three hits.

There is no carve-out anywhere: `.autodev/ARCHITECTURE.md:283` lists `STORE_RAW_PAYLOADS` as an env key with no per-model exception, no ADR narrows it, and `sed -n '/^## p02-/,$p' .autodev/DECISIONS.md` contains no bullet about dropping `raw` from any model. This is the one undocumented spec deviation in the phase.

Consequence for phase 3: `STORE_RAW_PAYLOADS=True` will be able to preserve the GraphQL response for organizations, repositories and PRs, but silently not for commits, reviews or review comments — which is precisely the data whose parsing (`co_authors`, `trailers`, review states, comment metadata) is hardest to debug after the fact, and `docs/CONFIGURATION.md` already advertises the flag as "sync stores the raw GitHub GraphQL response alongside the derived fields (more disk, easier debugging)". The phase goal is "every table in spec §4 exists"; five of them are missing a column the spec names in its first sentence. Fixing it now is one line per model plus a regenerated `0001_initial`; fixing it in phase 3 costs an extra migration and a second review of what was supposed to be settled here.

**Fix:** Add `raw = models.JSONField(_("raw payload"), null=True, blank=True)` to `activity.Commit`, `activity.Review`, `activity.ReviewComment` (and to `activity.PRFile` / `activity.CheckStatus` if the plan's "every GitHub-owned model" is meant literally), regenerate `apps/activity/migrations/0001_initial.py`, and rerun `make css` if the manifest shifts. Add a test asserting every model in the admin's READ_ONLY (GitHub-owned) set has a `raw` field, so the rule is enforced rather than remembered — or, if some of them are deliberately exempt, log that exemption as a `[p02-.../decision]` bullet in `.autodev/DECISIONS.md` and narrow PLAN.md's wording to match.

## [MINOR] `SyncRun.started_at` is `auto_now_add`, so an explicitly assigned start time is silently discarded
`apps/github_sync/models.py`

`SyncRun.started_at = models.DateTimeField(_("started at"), auto_now_add=True)` (models.py:17). `auto_now_add` makes the field non-editable and overwrites whatever the caller assigned on first save, without an error. Spec §4.8 lists `started_at` as an ordinary column, and the field is both the `ordering` key (`-started_at`) and an index. Phase 3's sync service is the natural place to write `SyncRun(started_at=timezone.now(), ...)` or to record a queued-then-started run; that assignment will be dropped on the floor with no warning, and `apps/github_sync/tests/test_models.py::test_ordering_puts_newest_run_first` cannot catch it because it never sets the field either. Compare `activity.PullRequest.created_at`, which is a plain `DateTimeField` precisely because the value comes from outside.

**Fix:** Make it `models.DateTimeField(_("started at"), default=timezone.now)` so the default still fires but an explicit value is honoured, and keep the ordering/index as they are.

## [MINOR] Historical migration pins itself to the live app registry and a current permission codename
`apps/accounts/migrations/0004_admin_permissions.py`

`grant_manage_settings()` calls `create_permissions(global_apps.get_app_config("catalog"), apps=global_apps, verbosity=0)` and then `Permission.objects.get(content_type__app_label="catalog", codename="manage_settings")`. This is the same class of coupling the r1 review flagged for `catalog/0002_app_setting_defaults.py` and that was fixed there (the seed loop was inlined against the model-free `SETTING_DEFS`): a historical migration reaching into the *current* app registry. If a later phase renames or drops `AppSetting.Meta.permissions`' `manage_settings`, or removes the model, `migrate` from zero fails inside this migration with a bare `Permission.DoesNotExist` rather than at the point of change. The reverse function has the same `.get()` with no guard. The forward `create_permissions` call itself is the documented workaround for post_migrate ordering and is fine; the unguarded lookup is the fragile part.

**Fix:** Use `Permission.objects.filter(content_type__app_label="catalog", codename="manage_settings").first()` and no-op with a comment when it is absent (mirroring the `RunPython.noop` reverse now used in `catalog/0002`), so a future rename degrades to "grant skipped" instead of "migrate from zero is broken".
