## [MINOR] full_row_count falls back to len(full_rows()) so four tables now build their rows twice per sync export
`apps/dashboards/tables.py`

`full_row_count()` (tables.py:166-178) uses `TableSpec.count_builder` only for `pull_requests`/`recent_prs` with no active text search; `projects`, `repositories`, `people` and `reviewer_load` have no count builder, so it returns `len(full_rows(...))`. `views.export_table` then calls `full_rows()` again for the export body (views.py:283, 300-301). Before the fix those rows were built once. Each build runs the entity queryset plus `compute_many()` for the metric columns; the second pass mostly hits the `compute()` FileBasedCache, so the cost is the repeated entity queries and row-dict construction rather than a full metric recompute — a real but bounded regression on exactly the tables the fix did not target. Correctness is unaffected: both calls produce identical row sets.

**Fix:** Have `full_row_count()` return the built row list (or memoise it per request) so the fallback path hands its rows to the caller instead of discarding them, e.g. `rows_or_count()` returning `tuple[int, list | None]` and `export_table` reusing the list when it is not None.
